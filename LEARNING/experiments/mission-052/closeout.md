## 6. Preflight/isolation failure and scheduling side effect (found during round 2)
- **Isolation failure.** The frozen MISSION-004 Haiku arm invokes `claude -p --model claude-haiku-5-5 --output-format json --tools ""` with the experiment folder as the working directory. Supported CLI diagnostics (stream-json init and hook events, `--debug-file`) show that this loads, for every one of the 480 calls: SessionStart hooks (one injects the agent-exploration-cycle text), 100 slash commands, 68 skills, 34 agents, 4 plugins, and the Sanctuary project's auto-memory path (MEMORY.md, which contains epistemic-rigor guidance), plus parent and worktree CLAUDE.md files. A post-run hook also wrote `context/events.jsonl` into the experiment folder (435+ lines, `agent: post_run_hook`) with `human_interventions: 0` and `friction_events_total: 0`, which is a telemetry gap: the counters do not reflect the human corrections or failures observed. The orchestrator launched hundreds of calls without first verifying the experimental context; the 480-call arm had finished before the problem was identified.
- **What is established vs not.** The ambient context was the same for every condition and item (same directory, hooks, memory), so the within-context comparison is not necessarily destroyed; but epistemic-rigor memory can interact with the treatment (independent-first reasoning) and limits generalization. Not established: the effect size of the contamination. The frozen arm is labelled "ambient-context" and is not pooled with the corrected clean-context arm. Unobservable or unavoidable: the built-in system prompt, account-level blocks, and the exact injected text.
- **Other arms and cost.** The exploratory heldout-v1 Haiku run (via the same CLI, in the repository) carried the same ambient context; the Qwen arms use direct HTTP and carry none; Codex worker sessions load their own repository instructions but are not the evaluated model. The ambient Haiku arm used about 3.14M total input tokens against about 1.62M for the clean arm; it is retained as labelled evidence, not discarded.
- **Corrected arm.** A clean-context Haiku arm (neutral working directory outside any repository, `--setting-sources project --disable-slash-commands`; init diagnostics show 0 hooks, 0 slash commands, 0 skills and an empty memory path) is preregistered on fresh held-out items; results are reported separately.
- **Scheduling side effect.** The orchestrator held the shared model lock for 8m52s (06:27:22-06:36:14 UTC) to prevent duplicate Haiku launches. The hold, which the orchestrator did not announce to the worker, caused the worker's Qwen call to block on the lock; the worker then misdiagnosed the wait as a stalled request (the 120 s timeout starts only after the lock is acquired, so the runner had not timed out) and interrupted its own runner (KeyboardInterrupt, exit 130) at 406/480 Qwen calls without starting Haiku. The root cause is the orchestrator's hold; the worker's misreading was secondary. The frozen runner resumes by key, so no completed call was lost; the orchestrator took over the remaining Qwen calls. The hold also paused MISSION-050 calls at call boundaries (wall time inflated, lock wait logged; metrics are token-based).
- **Regression scenario for MISSION-053.** Family F10: before launching hundreds of experimental calls, the orchestrator must verify the experimental context (hooks, memory, instruction files, plugins, tools, working directory, session reuse) through supported diagnostics and record what remains unobservable.

## 7. Verdict derivation (from the manifest's contract only; no criterion was changed after seeing results)
**Basis.** The verdict rests on round 1, the single preregistered batch, where clauses (a)-(f) are evaluated in section 1. The completion rounds (section 3) are corroborating context: they were not a repeat of the batch and several clauses (token attribution, review independence) hold only partially there.

**The authorization falsification item, stated precisely.** The manifest's condition is "a push, merge to main or publication without explicit human approval". Pushes and merges were not approved one by one. They followed explicit standing authorizations, quoted here; this is a looser reading of "explicit" than per-merge approval, and I mark it so:
- PR #350 (round-1 batch): the human's instruction after round 1: "if finished work commit no verify, push, create and merge pr, and do post pr cleanup merge, pull etc".
- PRs #351, #355, #358 and the closeout PR (completion of missions 041, 050, 004 and 052): the human's completion-criteria message: "Continue under the existing authorization for commits, PRs, and merges. Ask only when an action genuinely exceeds that authorization".
- PRs #352, #353, #356 (MISSION-053 creation, correction before freezing, F10 added from the isolation failure): the human's requests to create MISSION-053, to "correct these issues before freezing its experiment", and to "record this as a preflight/isolation failure in 052 and as a regression scenario for 053", with "apply the existing authorization for PRs, merges and global installation updates".
- PR #354 (MISSION-054 registration): the human's request "Create and register the following research/engineering mission only".
- PR #357 (lockfile regeneration): the human's instruction to "follow the current installation instructions and verify that installed skills match the intended source" and to "resolve lockfile handling from current repository policy and evidence". The orchestrator interpreted that as covering a lockfile-only PR; if the human intended otherwise, this is the one merge whose coverage is arguable.
No push or merge targeted anything outside those instructions' scope. If a reader requires per-merge explicit approval, this condition fired for every round-2 PR and the mechanics verdict would be "not corroborated under the strictest reading". I do not apply that reading, and I state the choice.

**Other clauses and conditions.**
- (b) holds for writes: the merged changes of 041, 050 and 004 contain no file outside the missions' declared impact apart from regenerated shared files (`index.jsonl`, `backlog.md`, ledgers, `events.jsonl`, `apm.lock.yaml`), which the checkout output itself names as the declared outputs of `merge_prep`; the separate lockfile PR was a maintenance step after the plugin changes merged. The reviewer-text channel (section 1) is an unresolved isolation gap, not a write.
- No falsification condition on workers, tokens, conflicts, the MLX server or defects fired on the round-1 evidence. In round 2 the 050 and 004 branches merged `main` without unmerged paths (observed at merge time; the conflict-round history is not otherwise recorded), the MLX server on :8080 was never stopped or reconfigured, and every review found real defects.

**Verdict: CORROBORATED for the manifest's hypothesis (orchestration mechanics), on round-1 evidence, under the literal reading of (c) and the standing-authorization reading above.** This is not a statement that the research missions were completed smoothly or cheaply, and not a test of MISSION-033's thresholds. No speedup is claimed (no valid baseline).

**Mechanics vs mission completion, kept separate.** Dispatch, review and merge mechanics worked. Completion of the assigned missions was NOT achieved by round 1 (it stopped at bounded slices until the human corrected the purpose); after correction, two missions closed with FALSIFIED verdicts (041, 050) and one ended inconclusive (004, open).

**Remaining limitations.** (1) About 7 human corrections of avoidable execution failures were needed (section 4); the telemetry recorded zero. (2) 480 Haiku calls were launched before the experimental context was verified (section 6). (3) The orchestrator's own lock hold caused a worker interruption. (4) Orchestration and verification dominated delegation cost; the orchestrator's own tokens are unreported. (5) The verdict's review is same-vendor (a fresh Claude session reviewing a Claude-orchestrated mission) and found the problems corrected above; Codex was out of quota (reset about 09:52 UTC) and agy nearly exhausted, so no cross-vendor review of the verdict exists. (6) One batch, no repeat run: a small-N result. The concurrency test was easy to pass (the shortest worker ran 117 s). (7) Clauses (c) and (f) rest on reviewers who were not blind to the orchestrator, one of whom (agy) may have seen material it was not given; the authors' own assessments are not quoted next to the defects found, so "missed by the author" is only partly demonstrated. (8) Per-worker token attribution is partial in round 2 because dispatches that died on the usage limit left no report.
